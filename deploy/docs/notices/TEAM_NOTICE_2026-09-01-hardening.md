# 📢 인프라 공지 — Jenkins 접속 주소 변경 + 서버 점검 결과 (2026-09-01)

## ⚠️ 먼저: Jenkins 접속 주소가 바뀌었습니다

| | 주소 |
| --- | --- |
| 이전 | ~~`http://j15e104.p.ssafy.io:8081`~~ (더 이상 접속되지 않습니다) |
| **변경** | **`https://j15e104.p.ssafy.io/jenkins/`** |

계정은 그대로입니다. 북마크를 바꿔주세요.

**왜 바꿨나:** Jenkins 컨테이너는 호스트의 Docker 소켓(`/var/run/docker.sock`)을 물고 root로 돕니다.
Jenkins를 잡으면 EC2 전체를 잡는 것과 같습니다. 그런 관문이 **인터넷 전체에 평문 HTTP로**
열려 있었고, 로그인 비밀번호가 암호화 없이 흐르고 있었습니다.

또 하나 중요한 사실: **Docker의 포트 publish는 UFW 방화벽을 우회합니다.** 방화벽에서 8081을
막아도 열립니다. 그래서 publish 주소 자체를 `127.0.0.1`로 바꿔 호스트 로컬 전용으로 만들고,
외부 접근은 nginx의 https를 거치도록 했습니다.

GitLab webhook URL도 함께 변경했습니다(설정 완료, 별도 조치 불필요).

## 점검해서 고친 것들

| 항목 | 문제 | 조치 |
| --- | --- | --- |
| Jenkins 노출 | 8081 인터넷 전체 공개, 평문 HTTP | 루프백 바인딩 + https `/jenkins/` 경유 |
| backend 시크릿 | 컨테이너 안에 `MYSQL_ROOT_PASSWORD`, `JENKINS_ADMIN_PASSWORD`, `GITLAB_TOKEN`이 들어가 있었음 | `env_file: .env` 제거, 필요한 키만 명시 전달 |
| DB 백업 | **백업이 전혀 없었음** | 매일 03:10 자동 덤프 + 14일 보관, 복구 스크립트 |

### 특히 짚어둘 것 — "고쳤는데 안 고쳐진" 문제

nginx 설정 파일을 **단일 파일로 bind mount**하고 있었는데, 이 방식은 파일의 inode에 고정됩니다.
`git pull`은 파일을 새 inode로 갈아끼우므로 **컨테이너는 영원히 옛 내용을 봅니다.**

오늘 실제로 겪었습니다. `/jenkins/` 프록시를 추가하고 `git pull` → `nginx -t` → `reload`까지
전부 성공했는데 아무것도 반영되지 않았고, 요청은 계속 frontend로 갔습니다. frontend placeholder가
아무 경로에나 200을 돌려주기 때문에 **겉보기에는 성공처럼 보였습니다.**

디렉터리를 마운트하면 디렉터리 inode는 안정적이라 안쪽 파일 교체가 그대로 보입니다.
**설정 파일을 고쳤을 때는 반영 여부를 응답 내용까지 확인하세요.** 상태 코드만으로는 부족합니다.

## 점검했는데 이미 정상이던 것

- UFW: 22/80/443만 허용, 외부 리스닝도 정확히 그 셋뿐
- 네트워크 격리: frontend는 DB에 닿지 못하고, ai는 외부에서 접근 불가 — 설계대로 동작
- mysql: 루프백 바인딩(`127.0.0.1:3306`)
- SSH: 공개키 전용, 비밀번호 인증 비활성
- 인증서: 89일 남음, 자동 갱신 리허설(`certbot renew --dry-run`) 성공
- 로그 로테이션: 전 컨테이너 10MB×3 적용됨
- 재시작 정책: 전 컨테이너 `unless-stopped`, Docker 부팅 자동시작 활성
- 디스크 5% 사용, 메모리 15GB + 스왑 4GB, OOM 이력 없음
- `.env`는 Git 이력에 올라간 적 없음

## 의도적으로 하지 않은 것

- **컨테이너 리소스 제한**: 메모리 15GB에 여유가 크고 OOM 이력이 없습니다. 잘못 잡으면
  정상 동작을 죽입니다. **AI 서버가 실제로 배포되는 시점에** 실측해서 정하는 게 맞습니다.
- **fail2ban**: SSH 비밀번호 인증이 이미 꺼져 있어(공개키 전용) 무차별 대입이 통하지 않습니다.
- **SSH 접속 IP 제한**: 팀원 IP가 유동적이고, 잘못 잠그면 복구 수단이 없습니다(UFW 상시 활성이 규정).
- **EC2 재부팅 테스트**: 자동 복구 조건(`unless-stopped` + Docker 부팅 활성)은 확인했습니다.
  실제 재부팅은 서비스 중단을 동반하므로 팀 합의 후 진행하는 게 좋겠습니다.

## 🔴 팀에 남은 숙제 하나

**백업이 같은 EC2 안에만 있습니다.** 인스턴스 자체가 사라지면 백업도 같이 사라집니다.
`.env`도 마찬가지로 EC2에만 존재합니다.

- 정기적으로 로컬이나 팀 저장소로 내려받는 절차가 필요합니다:
  ```
  scp -i J15E104T.pem ubuntu@j15e104.p.ssafy.io:~/backups/mysql/*.sql.gz ./
  ```
- `.env` 실값과 pem 키가 팀 비밀 저장소에 실제로 올라가 있는지 확인 부탁드립니다.

## 백업/복구 사용법

```bash
bash scripts/backup-mysql.sh                          # 즉시 백업 (자동은 매일 03:10)
bash scripts/restore-mysql.sh <덤프.sql.gz> --dry-run  # 덤프 검증만
bash scripts/restore-mysql.sh <덤프.sql.gz> --yes      # 실제 복구 (현재 데이터 덮어씀)
```
