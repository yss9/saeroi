# BRAND 대화형 AI 에이전트 Design

## Purpose

BRAND 담당자가 제품 하나를 만들려면 소재 조달부터 제품 등록까지 15개 이상의 화면을 순서대로 돌아다녀야 하고, 각 단계마다 MetaMask 서명이나 KakaoPay 결제가 끼어 있다.

```
마켓플레이스 검색 → 소재 견적 → 거래 생성 → 결제 → 배송 → 수령 확정
→ 가공업체 검색 → 가공 요청 → 견적 비교 → 견적 선택 → 결제 → 커스터디 이관(서명)
→ 가공 결과 승인 → 생산 배치 생성 → 투입 확정(서명) → 제품 모델 등록 → QR 발행
```

이 전 과정을 **대화창 하나 안에서** 끝낸다. 담당자가 만들고 싶은 제품을 말하면 에이전트가 부족한 정보를 되묻고, 공급업체와 가공업체를 찾아 제시하고, 견적을 비교해준다. 담당자는 대화창 안에서 **서명과 결제만** 한다. 대화 세션은 여정이 끝날 때까지 유지된다.

## Scope

**포함**

- BRAND 전용 대화형 에이전트. 소재 조달 → 가공 → 생산 → 제품 등록의 전체 여정
- 다중 턴 정보 수집, 공급/가공업체 탐색, 견적 비교
- 대화 말풍선 안의 확인 카드를 통한 지갑 서명·결제
- 담당자가 화면에서 이미 진행 중인 건의 조회
- 대화 세션의 영속화 (며칠~몇 주 유지)

**제외**

- 기존 저울 사진 OCR 경로(`/v1/vision/weight` 계약 불일치)는 이번 범위 밖이다
- 스트리밍 응답 (1단계는 요청–응답)
- 실시간 알림 연동 (SSE/WebSocket/푸시)
- 필수 가공 규칙의 **강제**(생산 투입 시 검증)는 별도 선행 작업으로 분리한다 — 아래 §필수 가공 참고
- CONSUMER / SUPPLIER / PROCESSOR 역할

## 현재 상태 — 확인된 사실

착수 전 코드베이스를 확인한 결과다. 설계의 전제이므로 남긴다.

- **AI Agent / 챗봇 / LLM은 코드베이스에 전혀 없다.** 완전한 그린필드다
- `ai/` 서비스는 **OCR 전용**이다. 엔드포인트는 `/health`, `/`, `/v1/ocr`, `/v1/evidence/weight` 뿐이고, `app/` 어디에서도 환경변수를 읽지 않는다
- **LLM API 키 플러밍이 없다.** 외부 API 키는 `KAKAO_REST_API_KEY`와 `KAKAOPAY_SECRET_KEY` 뿐이다
- **비동기 인프라가 없다.** `@Async`, `ApplicationEvent`, Redis, Kafka, 커스텀 `TaskExecutor`가 하나도 없다. `@Scheduled` 워커 4개만 있다
- **알림은 DB inbox 전용**이다. SSE/WebSocket/푸시가 없다
- **필수 가공 규칙이 없다.** `ProcessType` 8종은 브랜드가 자유롭게 고르는 값이고, 소재 출처·종류에 따른 검증이 없다

## Architecture

### 결정 1 — 에이전트 루프는 `backend`(Spring Boot)에 둔다

```
브라우저(React)  ──►  Spring Boot [agent 패키지]  ──►  GMS ──► Claude
                           │
                           ├─ 대화 세션 (MySQL)
                           └─ tool ──► 기존 도메인 서비스 (같은 프로세스)

ai 컨테이너는 OCR 전용으로 그대로 둔다
```

`ai` 서비스가 아니라 `backend`에 두는 이유는, 이 에이전트가 하는 일이 OCR 같은 무상태 추론이 아니라 **인증된 사용자 권한으로 DB를 쓰고 결제를 일으키는 것**이기 때문이다.

- **인가** — 모든 tool이 `SecurityContext`의 사용자로 기존 서비스를 호출한다. `ai`에 두면 JWT를 릴레이한 뒤 `ai`가 다시 `backend`를 호출해야 한다(순환 호출). `deploy/docker-compose.yml`이 지키는 "`ai`에는 필요한 키만 준다" 원칙도 깨진다
- **트랜잭션** — tool 실행이 기존 `@Transactional` 경계 안에서 일어난다. HTTP 왕복이 끼면 불가능하다
- **세션 영속화** — 대화 상태는 MySQL에 있어야 하는데 `ai`에는 DB 접속이 없다
- **재사용** — tool이 호출할 서비스가 전부 이미 Java에 있다

`ai`에 두면 얻는 건 Python LLM 생태계인데, tool 루프 자체는 프레임워크가 필요 없는 크기다. 잃는 것(인가·트랜잭션·세션)이 훨씬 크다.

### 결정 2 — 에이전트는 돈과 서명을 직접 하지 않는다

**이 설계에서 가장 중요한 안전 경계다.**

MetaMask 서명은 브라우저의 개인키로만 가능하고, KakaoPay 결제는 사용자가 PG 화면에서 승인해야 한다. 서버가 원리적으로 대신할 수 없다.

```
모델이 결제·서명 tool 호출
      │
      ▼
 ❌ 실행 안 됨. agent_pending_action 행만 생성
      │
      ▼
 대화 말풍선 안에 확인 카드 렌더
      │ 담당자 클릭
      ▼
 기존 KakaoPay / ContractService 경로로 실행
      │
      ▼
 결과가 대화로 돌아와 모델이 다음 단계 진행
```

"대화창에서 결제나 서명만 하면 된다"는 요구는 이 구조로 충족된다 — 사라지는 것은 **페이지 이동**이지, 에이전트가 대신 서명하는 것이 아니다.

**카드는 돈과 서명에만 띄운다.** 가공 요청 생성, 견적 선택 같은 결정은 대화로 합의한 뒤 모델이 바로 실행한다. 카드가 12번 뜨면 "대화창에서 결제·서명만" 이라는 목표와 멀어지기 때문이다.

이 분기는 **개별 tool이 아니라 tool 바깥(`AgentToolExecutor`)에 둔다.** tool을 새로 추가하는 사람이 실수로 우회할 수 없어야 한다.

### 결정 2-1 — 지갑 서명은 여러 번이다. 체인을 정본으로 삼아 재개한다

브랜드가 이 여정에서 서명하는 횟수를 세면 **7~8회**다.

| 구간 | 서명 | 사이에 대기가 있나 |
|---|---|---|
| 가공 | `createProcessingJob` → `markProcessingShipped` → `approveProcessingResult` (3회, 반송 수령 확인이 별도면 4회) | **있다** (가공업체가 수령·가공·반송) |
| 생산 | `createBatch` → `submitPlanAndLock` → `confirmProduction` → `linkProductItems` (4회) | **없다** (연속) |

생산의 4단계는 **컨트랙트가 순서를 강제한다** — 앞 단계를 건너뛰면 revert 하고 서버도 보고 순서를 검사한다(`useProductionChainSteps.ts`). 묶어서 한 번에 보내려면 컨트랙트에 multicall이 있어야 하는데 없고, 추가하려면 재배포가 필요하다. **서명 횟수 자체는 줄일 수 없다.**

진짜 위험은 횟수가 아니라 **실패 지점이 7~8개**라는 것이다. 5번째 서명에서 담당자가 거절하거나 브라우저가 닫히면, 온체인은 4단계까지 가 있고 대화에는 카드가 떠 있는 어정쩡한 상태가 된다. 여기서 이어갈 수 없으면 여정이 거기서 멈춘다.

#### 카드는 의도를 저장하고, 진행 상태는 체인에서 읽는다

**진행 단계를 카드에 저장해 정본으로 삼지 않는다.** 저장값과 체인이 어긋날 수 있기 때문이다 — 트랜잭션은 성공했는데 서버 보고가 실패하면 카드는 "2단계까지"인데 체인은 3단계다. 그 상태에서 3단계를 다시 서명하면 revert 한다.

그래서 **체인이 정본이다.**

```
카드           "생산 확정을 하기로 했다. batchId=42, 단계 4개"   ← 의도
체인           실제로 어디까지 갔는지                          ← 정본
result_json    지금까지의 txHash 목록                          ← 기록(로그)
```

카드를 그릴 때마다 프론트가 온체인 상태를 읽어 **다음에 할 단계를 정한다.** 기존 `useProductionChainStatus`(`DRAFT`/`SIGNING`/`CONFIRMED`)와 `getProcessingChainStatus`가 이미 그 값을 읽고 있으므로 그대로 쓴다.

이 설계는 부수 효과로 **담당자가 대화 대신 기존 화면에서 3단계를 눌렀을 때**도 자연히 처리된다 — 체인을 보면 이미 됐다는 걸 알고 건너뛴다.

#### 연속 서명은 한 카드로 묶는다

생산의 4단계는 중간에 담당자가 결정할 것이 없다. 카드를 4개 띄우지 않고 하나로 묶어 진행 상태를 보여준다.

```
┌────────────────────────────────┐
│ 생산 확정 — 서명 4회 필요        │
│  ① 배치 생성          ✅ 완료   │
│  ② 투입 잠금          ✅ 완료   │
│  ③ 소재 소각·확정      ⏳ 서명 중│
│  ④ 제품 연결                   │
│      [계속]  [나중에]           │
└────────────────────────────────┘
```

팝업 횟수는 같지만 담당자는 **하나의 작업**으로 인식하고, 어디까지 왔는지 보인다.

가공의 3회는 사이에 상대방 대기가 있으므로 **각각 별개 카드**다(단계 1개짜리 묶음). 단발과 묶음을 같은 구조로 다뤄 처리 경로를 하나로 유지한다.

#### 중간 단계는 모델을 부르지 않는다

②를 끝냈다고 LLM을 호출하면 크레딧이 4배로 든다. **마지막 단계가 끝났을 때만** 대화를 이어간다. 중간 보고는 카드 상태만 갱신한다.

#### 만료된 묶음은 되살리지 않는다

2단계까지 하고 하루 뒤 돌아오면 카드는 만료돼 있다. 만료된 카드를 이어 쓰지 않고 **폐기한 뒤, 대화가 체인 현황을 조회해 "생산이 2단계까지 진행됐습니다. 이어서 할까요?" 하고 새 카드를 발급**한다. 체인이 정본이라 새 카드도 정확히 3단계부터 시작한다.

### 결정 3 — 모든 제시에 근거를 붙인다

담당자가 에이전트의 말을 근거 없이 믿고 결제하는 상황을 막는다. 다만 **강제할 수 있는 것과 없는 것을 구분**한다.

**검증 가능한 것 — 구조로 강제한다.**
수량, 단가, 잔량, 납기 같은 숫자는 전부 tool 결과에서 나온다. 모델이 지어낼 수 없다.

- 모델이 제시하는 업체·판매글·금액은 직전 tool 결과에 있던 값이어야 한다
- 확인 카드의 요약은 **모델이 쓴 문장이 아니라 실제 실행될 인자**를 보여준다

**검증 불가능한 것 — 요구하되 출처를 표시한다.**
"폴리 혼방이라 열처리 전 색상 처리가 필요하다" 같은 추천 가공의 이유는 DB에 없는 일반 지식이라 서버가 참·거짓을 판정할 수 없다.

- 추천에는 반드시 이유를 붙이게 한다 (프롬프트로 강제)
- 화면에서 **필수와 추천을 시각적으로 구분**한다 — 필수는 규칙, 추천은 AI 판단임을 명시
- 추천은 담당자가 동의해야만 들어간다

담당자가 "이건 AI 의견" 임을 알고 판단하게 만드는 것이, 검증할 수 없는 것을 검증한 척하는 것보다 낫다.

### 결정 4 — tool은 로직을 갖지 않는다

전부 기존 서비스를 감싸기만 한다. 규칙을 복제하면 화면으로 한 것과 대화로 한 것의 결과가 갈라지고, 담당자가 어느 쪽을 믿을지 알 수 없게 된다.

| tool | 위임 대상 |
|---|---|
| 가공업체 검색 | `processing/service/ProcessorSearchService` |
| 가공 요청 생성 | `processing/service/ProcessingRequestService` |
| 견적 조회/선택 | `processing/service/ProcessingQuoteService` |
| 가공 결제 | `processing/service/ProcessingPaymentService` |
| 판매글 검색 | `trade/service/ListingQueryService` |
| 거래 생성 | `trade/service/TradeCommandService` |
| 소재 거래 결제 | `trade/service/PaymentService` |
| 내 소재/잔액 | `material/service/MaterialQueryService` |
| 생산 배치 | `production/` 서비스 |
| 제품 모델 | `product/` 서비스 |

## 여정 단계 모델

대화 하나가 제품 하나의 여정이다. 단계는 선형으로 흐르고, 각 단계의 체크 항목을 채워야 다음으로 넘어간다.

### 대화는 담당자당 하나만 진행한다

`ACTIVE` 대화는 담당자당 **1개**다. 새로 시작하려면 기존 것을 먼저 끝내야 한다.

여러 대화를 허용하면 "어느 대화에서 진행 중인 건인가"를 매번 따져야 하고, 같은 소재를 두 대화가 동시에 묶으려는 상황이 생긴다. 하나로 묶으면 그 문제가 통째로 사라진다.

### 종료는 담당자가 한다

단계가 끝까지 가지 않아도 담당자가 **완료 버튼**을 누르면 종료된다. 그때까지의 진행사항(생성된 거래·가공 요청·생산 배치)은 **모두 그대로 남는다** — 대화는 진행을 돕는 창구일 뿐, 도메인 데이터의 소유자가 아니다. 종료 후에도 담당자는 기존 화면에서 그 건들을 이어서 처리할 수 있다.

모델은 대화를 끝낼 수 없다. 모델이 닫아 버리면 담당자가 이어서 물을 수 없다.

### 되돌릴 수 있는 것은 되돌린다

이미 만든 거래·가공 요청 중 도메인이 취소를 허용하는 것은 대화에서도 취소할 수 있다. 기존 취소 API에 위임하며, 취소 가능 여부의 판정도 도메인이 한다.

| 단계 | 체크할 것 | 완료 조건 | 대기 구간 |
|---|---|---|---|
| `INTAKE` | 제품 종류, 소재 종류, 수량(g), 필요 공정, 납기, 예산 | 앞의 4개 필수 | — |
| `MATERIAL_SOURCING` | 보유 잔량, 부족분, 구매할 판매글, 결제, 수령 | 필요 수량만큼 **가용 잔량** 확보 | 판매자 배송 |
| `PROCESSING` | 업체, 공정, 견적, 결제, 커스터디 이관, 결과 승인 | 가공 결과 승인 → 산출 소재가 잔량에 들어옴 | 견적 도착, 가공 완료 |
| `PRODUCTION` | 투입 소재와 수량, 배치 확정 | 생산 배치 확정 | — |
| `PRODUCT` | 제품 모델 정보, 이미지, QR | 제품 모델 + QR 발행 완료 | — |
| `DONE` | — | — | — |

### 단계 전환은 코드가 검사한다

완료 조건을 코드로 쓰고 **DB 상태를 보고** 판정한다. 모델이 임의로 건너뛸 수 없다.

다만 예외가 필요하다 — 이미 소재를 충분히 갖고 있거나 가공이 필요 없는 경우가 있다. 그래서 **모델이 "2단계를 건너뛸까요?"를 담당자에게 묻고 동의를 받으면 건너뛴다.** 코드가 기본 게이트를 쥐고, 예외는 사람이 승인한다.

단계를 **뒤로 되돌리는 것은 막지 않는다.** "소재부터 다시 고를래" 는 정상 흐름이고, 되돌리지 못하면 필요한 tool이 노출되지 않아 대화가 막힌다.

### 단계별 tool 노출 (progressive disclosure)

전체 여정의 tool은 30개가 넘는다. 한꺼번에 넘기면 모델이 엉뚱한 단계의 tool을 부른다 — 소재도 안 샀는데 생산 배치를 열려는 식이다. **현재 단계의 tool만 넘긴다. 한 번에 10개 안쪽.**

노출만 좁히고 실행을 막지 않으면 의미가 없다. 모델이 이전 턴에서 본 tool 이름을 기억해 단계가 바뀐 뒤에도 부를 수 있으므로, **실행 시점에도 단계를 확인한다.**

단계를 잘못 옮겨도 **할 수 있는 일이 늘 뿐 권한은 늘지 않는다.** 어느 단계든 돈·서명은 카드를 거치고, 인가는 기존 도메인 서비스가 본다. 최악은 "엉뚱한 tool이 보이는 것"이다.

### 대기 구간

여정에는 상대방(판매자·가공업체)이 움직여야 넘어가는 구간이 세 군데 있다. 며칠~몇 주 걸린다.

알림이 DB inbox뿐이라 대화가 먼저 알 방법이 없다. **담당자가 물을 때마다 현황을 조회해서 알려준다.** 별도 인프라를 만들지 않는다.

### 기존 진행 건 이어받기

담당자가 화면에서 진행 중인 건도 대화가 읽는다. "어제 넣은 가공 요청 견적 왔어?"에 답할 수 있어야 한다.

대화 시작 시 단계는 **DB 상태에서 역산**한다.

## 필수 가공

### 2층 구조

```
필수 가공   ── 규칙으로 정해져 있음. 소재 출처·종류로 결정
              담당자가 뺄 수 없음
    +
추천 가공   ── 만들려는 제품과 원단 특성을 보고 모델이 판단
              담당자가 받아들이거나 뺄 수 있음
    ↓
합쳐서 가공 요청 생성
```

**필수 공정은 모델에게 맡기지 않는다.** 가공 요청을 만드는 tool이 인자에 필수 공정이 빠져 있으면 **자동으로 채워 넣는다.** 모델이 잊어도 결과가 같다.

**추천은 모델이 한다.** 제품·원단 특성을 보고 이유와 함께 제안하고, 담당자가 동의한 것만 들어간다. 여기는 모델의 판단이 실제로 필요한 자리다.

모델이 잘하는 일(맥락을 보고 제안)과 못 믿을 일(규칙을 빠짐없이 지키기)을 나눈다.

### 강제 지점은 생산이다 — 별도 선행 작업

필수 가공을 거치지 않은 소재로는 **제품을 생산해서 올릴 수 없다.** 가공 요청 자체는 막지 않는다.

기존 데이터만으로 검사가 가능하다. 스키마 변경이 필요 없다.

```
투입하려는 소재
   └─ material_lineage (relation_type=PROCESSING, reference_id=processing_job_id)
        └─ processing_job.processing_request_id
             └─ processing_request_type.process_type[]   ← 적용된 공정
   └─ 계보를 위로 거슬러 올라가며 공정을 합집합으로 모음
```

계보 순회는 `MaterialLineageQueryService`에 이미 있다(깊이 제한·순환 방지 포함). `root_origin`은 가공해도 바뀌지 않으므로 규칙 기준으로 안정적이다.

**이 검증은 에이전트와 무관하게 성립하는 도메인 규칙이므로 별도 작업으로 분리한다.** 에이전트는 그 규칙을 *읽어서* 미리 안내하는 쪽이다. (A) 도메인 검증이 없으면 화면으로 빠져나갈 수 있고, (A)만 있어도 플랫폼은 온전하다.

**미결 사항** — 아래는 아직 정하지 않았다.

- 필수 가공 표의 실제 내용 (`root_origin` 기준인지, `material_type`까지 보는지)
- "거쳤다"의 근거 — `processing_request_type`은 브랜드가 *요청한* 공정이다. "결과가 승인된 가공 작업의 요청 공정"을 수행 근거로 볼지
- 막는 시점 — 생산 배치 투입 / 생산 확정 / 제품 등록 중 어디. **투입 시점**이 가장 이르고 친절하다
- 기존 데이터 소급 여부 — 이미 판매 중인 제품이 위반 상태가 될 수 있다

## 데이터 모델

`schema.sql`이 정본이고 `ddl-auto: validate`이므로 **`schema.sql` 수정 + `db/migrations/*.sql` 추가**를 함께 한다. `scripts/verify-migrations.sh`가 CI에서 대조한다.

ERD 관례를 따른다 — `@ManyToOne` 없이 FK id를 raw 필드로 들고, `BaseEntity`로 auditing을 받는다.

### `agent_conversation`

여정 하나. 담당자가 끝낼 때까지 살아 있다.

| 컬럼 | 설명 |
|---|---|
| `brand_user_id` | 소유자 |
| `phase` | `JourneyPhase`. VARCHAR — 단계는 앞으로 늘어날 값이라 DB ENUM을 쓰면 값 추가마다 마이그레이션이 붙는다 |
| `status` | ACTIVE / COMPLETED / ABANDONED |
| `requirement_json` | 수집된 요구사항 스냅샷 |

`requirement_json`을 따로 두는 이유 — 여정 전체가 한 대화라 메시지가 수백 개가 되고 앞부분을 잘라내야 하는데, 그때 "데님 2kg으로 에코백"이 함께 사라지면 모델이 같은 것을 다시 묻는다. 이 값은 매 턴 시스템 프롬프트로 다시 들어가 잘리지 않는다.

### `agent_message`

LLM에 되먹일 이력. tool 호출과 결과도 포함한다.

`sequence_no`로 정렬하고 `created_at`으로 정렬하지 않는다. 한 턴 안에서 assistant 메시지와 tool 결과가 같은 초에 여러 개 쌓이는데, 시각만으로는 순서가 흔들린다. 순서가 어긋난 이력을 모델에 넣으면 tool 호출과 결과의 짝이 깨진다.

SYSTEM 역할은 저장하지 않는다. 시스템 프롬프트는 매번 조립한다 — 저장하면 프롬프트를 고쳤을 때 예전 대화만 옛 규칙으로 돌아 재현이 안 된다.

### `agent_pending_action`

확인 카드. **돈과 서명에만 생긴다.**

| 컬럼 | 설명 |
|---|---|
| `action_type` | WALLET_SIGN / PAYMENT |
| `tool_name` | 승인 시 실행할 tool |
| `summary` | 카드에 보여줄 한 줄 |
| `payload_json` | 실행할 인자 |
| `status` | PENDING / COMPLETED / REJECTED / EXPIRED |
| `result_json` | 담당자가 만든 결과 (txHash, pgToken) |
| `expires_at` | 기한 |

`expires_at`은 오래 방치된 제안이 되살아나는 것을 막는다 — 어제 열어둔 카드를 오늘 누르면 그 사이 재고나 가격이 바뀌었을 수 있다.

**다단계 서명을 위한 필드**

| 컬럼 | 설명 |
|---|---|
| `step_total` | 이 카드가 요구하는 서명 횟수. 단발은 1 |
| `step_done` | 지금까지 보고된 횟수. **정본이 아니라 표시용** |

`payload_json` 에 단계 정의가 들어간다.

```json
{
  "batchId": 42,
  "steps": ["CREATE_BATCH", "SUBMIT_PLAN", "CONFIRM", "LINK_ITEMS"]
}
```

`result_json` 에 각 단계의 결과가 쌓인다.

```json
{"completed": [
  {"step": "CREATE_BATCH", "txHash": "0x...", "at": "..."},
  {"step": "SUBMIT_PLAN",  "txHash": "0x...", "at": "..."}
]}
```

**`step_done` 을 신뢰하지 않는다.** 프론트는 카드를 그릴 때마다 온체인 상태를 읽어 다음 단계를 정하고, `step_done` 은 대화 이력과 화면 표시에만 쓴다. 둘이 어긋나면 체인이 이긴다.

JSON 성격 컬럼은 `TEXT`다. 이 스키마에 JSON 타입 컬럼이 아직 없고, 테스트가 H2(MODE=MySQL)로 도는데 H2의 JSON 타입은 Hibernate 매핑이 MySQL과 다르다.

### 저장소는 MySQL — Redis를 쓰지 않는 이유

채팅이라 Redis를 검토했으나 MySQL로 결정했다. 근거를 남긴다.

**성능은 논점이 아니다.** 한 턴의 DB 시간은 약 15ms인데 같은 턴의 LLM 호출이 20,000ms다. Redis로 바꾸면 20,015ms가 20,003ms가 된다 — 0.06%다. 이 워크로드의 병목은 저장소가 아니다.

| 실제로 먼저 깨지는 것 | 시점 | Redis가 해결? |
|---|---|---|
| DB 커넥션 풀 | 동시 10명 | ❌ (트랜잭션 경계 문제다) |
| 크레딧 소진 | 동시 5~10명이 하루 | ❌ |
| GMS 레이트 리밋 | 팀 키 한도 | ❌ |
| MySQL 조회 성능 | 수천만 행 이후 | ✅ (하지만 한참 뒤) |

**트랜잭션이 결정적이다.** 카드 승인은 "도메인 쓰기 + 카드 상태 전이"가 한 트랜잭션이어야 한다. 대화가 Redis에 있으면 저장소가 갈려서, 도메인은 커밋됐는데 Redis 쓰기가 실패하면 카드가 `PENDING`으로 남고 담당자가 다시 눌러 **결제가 두 번 나간다.**

**이 대화는 캐시가 아니라 사업 기록이다.** 몇 주에 걸쳐 무엇을 얼마에 샀는지, 담당자가 무엇에 동의했는지가 남는다. `deploy/scripts/backup-mysql.sh`가 이미 도는 백업 체계에 Redis는 들어 있지 않다.

**조회가 대화 하나로 한정된다.** `WHERE conversation_id = ? ORDER BY sequence_no`는 인덱스가 덮고 60건만 읽는다. 행이 3,000만 개가 되어도 조회는 ~3ms다. 게다가 대화 이력은 계속 추가되는 데이터라 캐시 적중률이 낮다 — 캐시가 잘 듣는 모양이 아니다.

규모가 실제로 커지면 필요한 것은 Redis가 아니라 **종료된 대화의 아카이빙**이다.

## API 계약

```
POST   /api/v1/agent/conversations                 새 대화 시작 (첫 발화 포함)
GET    /api/v1/agent/conversations/active          진행 중인 대화 (없으면 null)
GET    /api/v1/agent/conversations                 내 대화 목록 (종료된 것 포함)
GET    /api/v1/agent/conversations/{id}            이력 + 대기 중 카드
POST   /api/v1/agent/conversations/{id}/messages   발화 → 에이전트 턴 실행
POST   /api/v1/agent/conversations/{id}/complete   담당자가 완료 처리
POST   /api/v1/agent/actions/{actionId}/step       다단계 서명의 중간 단계 보고
POST   /api/v1/agent/actions/{actionId}/complete   서명/결제 결과 회신 (마지막 단계)
POST   /api/v1/agent/actions/{actionId}/reject     담당자 거절
```

`/step` 과 `/complete` 를 나누는 이유는 **모델 호출 시점을 다르게 하기 위해서다.** `/step` 은 카드 상태만 갱신하고 LLM을 부르지 않는다(중간 단계마다 부르면 크레딧이 단계 수만큼 든다). `/complete` 만 대화를 이어간다.

`/step` 은 보고된 단계가 **순서에 맞는지** 검사한다. 컨트랙트가 revert 로 막아주지만, 그 전에 서버가 거른다.

`ACTIVE` 대화가 이미 있는 상태에서 `POST /conversations`를 부르면 새로 만들지 않고 **기존 대화를 돌려준다.** 대화 창을 다시 열었을 때 이어서 진행하는 것이 정상 동작이다.

전부 `ApiResponse<T>` 봉투. `SecurityConfig`의 permitAll 목록에 넣지 않는다.

**BRAND 인가는 `@PreAuthorize`가 아니라 서비스 계층에서 DB 재조회로 검사한다.** 이 저장소의 인가 정본이 그렇고(`specs/2026-09-08-role-permission-matrix.md:49-57`), "이 대화가 내 것인가"는 토큰 claim으로 표현할 수 없어 어차피 서비스가 봐야 한다.

대화 소유권은 **조회 쿼리 자체에 소유자를 박는다**(`findByIdAndBrandUserId`). `findById` 후 서비스에서 비교하면, 비교를 빠뜨린 경로가 하나라도 생기는 순간 남의 대화가 새어 나간다.

**스트리밍은 1단계에서 하지 않는다.** `frontend/src/services/apiClient.ts`가 봉투를 벗기는 인터셉터와 10초 타임아웃을 갖고 있어 SSE와 맞지 않고, 백엔드에 비동기 인프라가 없다. 요청–응답으로 하되 턴 타임아웃을 넉넉히 잡고 프론트가 "생각 중"을 보여준다.

## LLM 연동 (GMS)

### GMS는 Anthropic 네이티브 API 패스스루다

```
POST https://gms.ssafy.io/gmsapi/api.anthropic.com/v1/messages
헤더: x-api-key: $GMS_KEY
      anthropic-version: 2023-06-01
```

원본 API 호스트를 경로에 끼워넣는 구조다. **OpenAI 호환 `chat/completions`가 아니라 Anthropic Messages API 그대로**이므로, 클라이언트는 Anthropic 형식으로 구현한다.

| | OpenAI | **Anthropic (이쪽)** |
|---|---|---|
| 시스템 프롬프트 | `messages[0].role="system"` | 최상위 `system` 필드 |
| tool 정의 | `{type:"function", function:{...}}` | `{name, description, input_schema}` |
| tool 호출 | `message.tool_calls[]` | `content[]`의 `tool_use` 블록 |
| tool 인자 | JSON **문자열** | 이미 파싱된 **객체** |
| tool 결과 | `role:"tool"` 메시지 | `user` 메시지 안의 `tool_result` 블록 |
| `max_tokens` | 선택 | **필수** |

tool 인자가 객체로 오는 것은 유리하다 — 모델이 만든 JSON 문자열을 파싱하다 실패하는 경로가 사라진다.

### 공급자 교체 지점

호출을 `LlmClient` 인터페이스 뒤에 둔다. 구현체는 Anthropic 형식 한 벌. 실패는 전부 `AGENT_LLM_UNAVAILABLE`로 번역한다 — `vision/service/WeightVisionClient`와 같은 방식이다.

키가 비어 있으면 `UnavailableLlmClient`로 대체해 기동은 되되 호출 시 503을 낸다. `PaymentGatewayConfig`가 KakaoPay 시크릿이 없을 때 mock으로 대체하는 것과 같다 — 이 키 하나 때문에 소재 등록·결제까지 못 뜨게 할 이유가 없다.

**대화 본문을 로그에 남기지 않는다.** 담당자가 쓴 사업 정보가 그대로 들어 있다. 상태·지연·tool 이름만 남긴다.

## 크레딧 제약

**이 기능의 가장 큰 제약이다.**

팀 크레딧 100,000, 토큰당 차감. `claude-sonnet-4-6` 기준 입력 0.03 / 출력 0.15.

에이전트는 사용자가 한 번 말할 때 LLM을 여러 번 부른다. tool을 3번 부르면 LLM 호출이 4번이다.

| | 크레딧 |
|---|---|
| LLM 호출 1회 (입력 8K, 출력 400) | ~300 |
| 사용자 발화 1회 (LLM 4회) | ~1,200 |
| 여정 1건 (40턴) | ~28,000 |
| **100,000으로 가능한 총량** | **약 140턴 / 여정 3~4건** |

개발 테스트까지 포함해 전부 합쳐서다. 저울 OCR 등 다른 기능과도 공유한다.

### 절약 설계

**① 개발의 대부분은 LLM을 부르지 않는다**

| 단계 | 모델 | 용도 | 크레딧 |
|---|---|---|---|
| 0. 스텁 | 없음 | 로직·안전장치·회귀 테스트 | **0** |
| 1. 배선 | `claude-haiku-4-5-20251001` | GMS 연결, tool 파싱, E2E | 낮음 |
| 2. 품질·시연 | `claude-sonnet-4-6` | 프롬프트 다듬기, 시연 | 높음 |

개발 기간의 대부분은 0단계다. tool 루프가 도는지, 쓰기가 카드로 막히는지는 진짜 모델이 필요 없다.

**Haiku로 대화 품질을 판단하지 않는다.** 여러 단계 tool 연쇄에서 Sonnet보다 약해서, Haiku에 맞춰 프롬프트를 다듬으면 잘못된 대상에 튜닝하게 된다. Haiku는 "돌아가는가"만 본다.

**② 모델과 thinking을 프로퍼티로 뺀다**

Sonnet 4.6은 adaptive thinking과 `effort`를 지원하지만 **Haiku 4.5는 그 둘을 거부한다.** 같은 코드로 모델만 바꾸면 400이 난다. 기본은 thinking을 끄고, Sonnet으로 올릴 때 켠다.

thinking 토큰은 출력 토큰(0.15)이라 5배 비싸다. `effort`를 낮게 두고 시작해 tool 선택이 흔들리면 올린다.

**③ `max-tool-iterations` 를 4로**

8이면 최악의 경우 한 발화에 9회 호출, 2,700 크레딧이다.

**④ 프롬프트 캐싱**

tool 루프는 한 턴 안에서 같은 접두사를 4번 다시 보낸다. 시스템 프롬프트 + tool 명세 + 이력이 매번 반복된다. 캐시가 먹으면 2~4번째 호출의 입력 비용이 통상 10분의 1로 떨어져 가용 턴이 2~3배가 된다.

접두사가 안정적이라(이력이 뒤에 덧붙는 append-only) 캐싱에 이상적인 구조다. **다만 GMS가 캐시 토큰을 어떻게 과금하는지는 안내에 없다** — 실제 호출 후 `usage.cache_read_input_tokens`와 사용 현황을 대조해 확인해야 한다.

**⑤ 단계별 tool 노출과 이력 자르기**

tool 명세도 입력 토큰이다. 30개를 매번 보내는 것과 8개만 보내는 것은 차이가 크다.

## 턴 오케스트레이션

```
사용자 발화 저장
  └→ (최대 max-tool-iterations 회 반복)
       LLM 호출 → tool 호출이 있나?
         ├ 있다 → 읽기면 실행, 돈·서명이면 카드 생성
         │        → 결과를 이력에 넣고 다시 호출
         └ 없다 → 그 답이 이 턴의 결론. 저장하고 종료
```

상한에 걸리면 **장애로 취급하지 않고 담당자에게 되묻는다.** 모델이 스스로 정리하지 못했을 뿐이고, 더 구체적인 입력을 받으면 풀리는 경우가 대부분이다.

### 트랜잭션은 LLM 호출을 감싸지 않는다

**턴 전체를 하나의 트랜잭션으로 묶으면 안 된다.** 그렇게 하면 DB 커넥션을 LLM 응답이 올 때까지(20~30초) 쥐고 있게 된다.

`application.yml`에 Hikari 설정이 없어 **커넥션 풀은 Spring Boot 기본값 10개**다. 즉 **동시 10명이 대화하면 풀이 고갈되고, 에이전트뿐 아니라 소재 등록·결제·로그인까지 앱 전체가 멈춘다.** 회원이 조금만 늘어도 닿는 숫자다.

```
❌ 하지 말 것                     ✅ 이렇게

@Transactional {                  [트랜잭션] 발화 저장          2ms
  발화 저장                        LLM 호출         20초 ← 커넥션 없음
  LLM 호출   ← 20초 점유           [트랜잭션] tool 실행·결과 저장  5ms
  tool 실행                        LLM 호출         20초 ← 커넥션 없음
  답변 저장                        [트랜잭션] 답변 저장          2ms
}
```

커넥션 점유가 20초에서 10ms 미만으로 줄어, 같은 풀 10개로 동시 수백 명을 받는다.

**대가** — 턴 중간에 실패하면 반쯤 진행된 이력이 남는다. 이건 감당한다. 다음 턴에 모델이 그 이력을 보고 이어가면 되고, 오히려 사용자에게는 진행이 보존되는 편이 낫다.

**유지되는 것** — 쪼개는 것은 **대화 이력 저장 쪽뿐이다.** 확인 카드 승인 시의 "도메인 쓰기 + 카드 COMPLETED 전이"는 **한 트랜잭션으로 남는다.** 결제가 두 번 나가는 것을 막는 보장은 건드리지 않는다.

### 커넥션 풀을 명시적으로 설정한다

기본값 10은 이 앱에 작다. 결제 만료·가공 만료 등 `@Scheduled` 워커 4개도 같은 풀을 쓴다. `spring.datasource.hikari.maximum-pool-size`를 명시한다.

### tool 실패를 예외로 던지지 않는다

조회 결과 0건, 모델이 인자를 잘못 채운 것, 도메인 규칙 위반(재고 부족 등)은 **장애가 아니라 모델이 알아야 할 사실**이다. 결과 JSON으로 돌려주면 모델이 담당자에게 이유를 설명하고 다른 수를 제안한다. 예외로 던지면 대화 전체가 끊긴다.

### 이력 자르기

최근 N개만 모델에 넣되, 앞을 자를 때 **tool 결과가 그 호출보다 먼저 나오는 상태로 시작하면 안 된다.** 짝이 맞지 않는 tool 메시지는 거부된다. 잘라낸 첫 메시지가 고아 tool 결과이면 짝이 맞을 때까지 더 버린다.

잘려 나간 앞부분의 요구사항은 `requirement_json`으로 시스템 프롬프트에 다시 들어간다.

### 대화는 별도 창으로 띄운다

```
┌─────────────────────────┬──────────────────┐
│  기존 화면               │  AI 대화 창       │
│  (소재 목록, 가공 요청…) │  담당자와 대화    │
│  보면서 확인할 수 있음    │  카드로 서명·결제 │
└─────────────────────────┴──────────────────┘
```

AI 버튼을 누르면 `window.open(url, 'saeroi-agent')`로 **이름 있는 창**을 연다. 이름을 주면 버튼을 다시 눌러도 새 창이 생기지 않고 기존 창이 앞으로 나온다 — 같은 대화를 두 곳에서 여는 문제를 브라우저가 막아준다.

**창 간 토큰 동기화가 필요하다.** 이 프로젝트의 Refresh Token은 한 번 쓰면 회전하고 기존 것을 무효화한다(`RefreshTokenService`: `revokeIfActive(...) != 1`이면 거절). Access Token 수명이 30분이라 두 창이 거의 동시에 만료를 맞고, 둘 다 재발급을 시도하면 하나가 실패해 **세션이 통째로 비워진다.** 세션은 `localStorage` 공유라 **두 창 모두 로그아웃된다.**

`apiClient`의 동시 재발급 단일화는 **한 창 안에서만** 동작하므로, `BroadcastChannel`(또는 `storage` 이벤트)로 창 간에 재발급을 조율한다 — 한 창이 재발급하는 동안 다른 창은 기다렸다가 새 토큰을 받아 쓴다. 이 장치는 에이전트 외의 다른 멀티탭 상황도 함께 안전하게 만든다.

결제 리다이렉트는 이 창 안에서 돌고 돌아온다(팝업 차단 주의).

- 라우트는 `src/app/router/routes.tsx`에만 추가한다 (`RoleGuard allow={['BRAND']}`)
- `sendMessage`는 `recognizeWeight.ts`가 보여주는 per-call 타임아웃 override 패턴을 쓴다
- 지갑 서명은 컴포넌트에서 `new ethers.Contract`를 만들지 않고 기존 `features/{domain}/services/*ContractService.ts`를 경유한다. 주소·ABI는 `config/contracts.ts` + `config/abi/`에서만 온다
- tool 호출·결과 줄은 화면에 그리지 않는다. 담당자가 읽을 것은 모델의 말과 카드다

### 결제 복귀 경로 신설이 필요하다

현재 `KAKAOPAY_RETURN_URL`/`KAKAOPAY_PROCESSING_RETURN_URL`은 `/trades/{tradeId}/...`, `/processing/jobs/{jobId}/...`로 고정돼 있다. 대화창에서 결제하면 돌아올 곳이 대화여야 하므로 `/agent/{conversationId}/payment/callback` 경로와 대응 프로퍼티를 추가한다.

이 값은 `deploy/.env.example`에 실운영 도메인으로 넣어야 한다 — 기존 리턴 URL이 비어 localhost로 깨진 사고가 `.env.example`에 기록돼 있다.

## 온체인 미등록 판매글 — 걸러내지 않고 구분한다

`material_listing.chain_listing_id` 가 `NULL` 인 판매글이 정상적으로 존재한다. `ListingCommandService` 주석:

> 등록된 판매 글은 `chain_listing_id` 가 `NULL` 이다. 이것이 **"등록됐지만 아직 온체인에 없음" 상태**이며, 응답이 그대로 내려보내 **화면이 구분할 수 있게 한다**

플랫폼이 정식으로 지원하는 상태이므로 **에이전트가 더 엄격한 규칙을 혼자 만들지 않는다.** 후보에서 걸러내지 않고, 목록에 온체인 여부를 표시한다.

- 온체인 등록된 판매글에만 체인 서명 카드가 뜬다
- 미등록 판매글도 구매·결제·수령까지 정상 동작한다 (잔액 이전은 DB 작업이다)
- 대화가 그 차이를 담당자에게 알린다

걸러내면 개발 환경에서 검색이 항상 0건이 되어 대화가 막힌다. 구분 표시로 두면 **개발과 시연이 같은 코드로 돈다.**

## 테스트 데이터

온체인 트랜잭션 없이 대화 전 과정을 테스트할 수 있다. 근거:

- `ListingCommandService` — "**DB 만 채운다**. 온체인 `createListing` 은 별도 경로다"
- `TradeShipmentService`, `TradeReceiptService` — 체인 참조가 **없다.** 수령 확정의 잔액 이전은 순수 DB 작업이다
- `User.register()` — 가입 즉시 `ACTIVE`. 관리자 승인이 서버 기능을 막지 않는다
- `MockPaymentGateway` — `KAKAOPAY_SECRET_KEY` 가 비면 자동 대체, 실제 청구 없음

**단, 지갑은 필요하다.** `OffChainMaterialIssuer` 주석: "**지갑이 없으면 발행하지 않는다.** 거래 생성도 양쪽 활성 지갑을 요구한다". 지갑 등록은 `personal_sign` 이라 가스도 체인 기록도 없고 **계정당 한 번**이면 된다.

| 데이터 | `chain_listing_id` | 대화·거래·결제·수령 | 온체인 서명 |
|---|---|---|---|
| 시드 | `NULL` | ✅ | 카드가 뜨지 않음 |
| **가짜 ID 주입** | `999` | ✅ | ❌ **revert — 절대 금지** |
| 실제 등록 | 진짜 값 | ✅ | ✅ |

**가짜 온체인 ID를 넣지 않는다.** DB가 "온체인에 있다"고 주장하는데 체인에 없으면 서명이 revert 하고, 원인을 찾기 어렵다.

시연 데이터는 실제 등록 **1건이면 충분하다.** `TradeCreateRequest` 가 부분 구매를 전제하므로, 100kg짜리 판매글 하나로 2.4kg씩 40회 시연할 수 있다.

## 서명 실패와 복구

서명이 7~8회라 실패 지점도 그만큼이다. 각 실패에서 **체인·서버·대화 세 곳의 상태가 어떻게 어긋나고 어떻게 맞추는지**를 정한다.

| 상황 | 체인 | 서버 | 복구 |
|---|---|---|---|
| 담당자가 서명 거절 (4001) | 변화 없음 | 변화 없음 | 카드를 `PENDING`으로 유지. 오류가 아니라 선택이므로 "다시 진행할까요?" 로 묻는다 |
| 가스 부족·tx revert | 변화 없음 | 변화 없음 | 위와 같음. 실패 사유를 대화에 남긴다 |
| tx 성공 직후 브라우저 종료 | **앞섬** | 뒤처짐 | 재개 시 체인을 읽어 이미 끝난 단계를 건너뛴다 |
| tx 성공, `/step` 보고 실패 | **앞섬** | 뒤처짐 | 같음. `step_done` 이 아니라 체인이 기준이라 자동으로 맞는다 |
| 담당자가 기존 화면에서 다음 단계를 진행 | **앞섬** | 맞음 | 체인 조회로 감지해 건너뛴다. 대화와 화면이 충돌하지 않는다 |
| 카드 만료 후 복귀 | 중간 | 중간 | 만료 카드는 폐기. 현황을 조회해 새 카드를 발급하고 남은 단계만 담는다 |
| 마지막 단계까지 끝남 | 완료 | 완료 | `/complete` 로 카드를 닫고 대화를 이어간다 |

### 재개 흐름

```
담당자가 대화 창을 다시 연다
   │
   ├─ GET /conversations/active  → PENDING 카드가 있다
   │
   ├─ 프론트가 온체인 상태 조회        ← 체인이 정본
   │    "생산 배치 42: SIGNING (2단계까지)"
   │
   ├─ 카드에 ①② 완료, ③부터 표시
   │
   └─ [계속] → ③ 서명 → /step → ④ 서명 → /complete
```

**체인을 읽는 것은 프론트다.** 서버가 읽으려면 backend에서 RPC를 호출해야 하는데, 이미 프론트가 컨트랙트를 읽는 경로(`useProductionChainStatus`, `getProcessingChainStatus`)를 갖고 있고 지갑도 거기 있다. 서버에 같은 조회를 또 만들면 두 벌이 된다.

다만 **대화가 현황을 설명하려면 모델도 알아야 하므로**, 체인 상태를 읽는 조회 tool을 하나 둔다. 이 tool은 서버의 `blockchain_transaction` 기록과 도메인 상태를 읽는다(RPC를 새로 부르지 않는다) — 설명에는 그 정도로 충분하고, 정확한 다음 단계 판정은 프론트가 체인에서 한다.

### 이미 끝난 단계를 다시 서명하지 않는다

컨트랙트가 revert 로 막지만, 그 전에 두 곳에서 거른다.

- **프론트** — 체인 상태를 읽어 다음 단계만 활성화한다
- **서버** — `/step` 보고가 순서에 맞지 않으면 거절한다

## Testing Strategy

house style은 full-context `@SpringBootTest` + `MockMvc` + H2다(`@WebMvcTest`는 175개 중 2개). `src/test/resources/application.yml`이 운영 yml을 **교체**하므로 `app.agent.*` 테스트 값을 거기 넣는다.

`LlmClient`를 `@MockitoBean`으로 스텁한다. 진짜 모델을 부르면 같은 입력에 다른 출력이 나와 테스트가 흔들리고, 여기서 확인할 것은 모델의 판단이 아니라 **모델이 무엇을 하든 우리 쪽이 지키는 것**이다. 크레딧도 들지 않는다.

**핵심 안전 테스트**

- 돈·서명 tool이 **카드만 만들고 DB를 바꾸지 않는다**
- 승인해야 실제 도메인 서비스가 호출된다
- 같은 카드를 두 번 승인할 수 없다 (두 번 실행이 이 구조에서 가장 위험한 버그다)
- 남의 대화·남의 카드를 건드릴 수 없다
- 단계에 없는 tool은 모델이 불러도 실행되지 않는다

**그 밖**

- tool 루프: 호출 → 실행 → 결과 재투입 → 최종 응답
- `max-tool-iterations` 초과 시 503이 아니라 되묻기
- 도메인 거절이 대화에 설명으로 남는다
- GMS 연결 실패·타임아웃이 `AGENT_LLM_UNAVAILABLE`로 변환된다
- 대화 종료 시 떠 있던 카드도 닫힌다
- BRAND가 아니면 거절
- `ACTIVE` 대화가 있으면 새 대화를 만들지 않고 기존 것을 돌려준다
- 담당자가 완료하면 그때까지 만들어진 도메인 데이터(거래·가공 요청)는 그대로 남는다
- **LLM 호출이 트랜잭션 밖에서 일어난다** — 커넥션 점유 시간을 검증한다
- 카드 승인의 "도메인 쓰기 + 상태 전이"는 여전히 한 트랜잭션이다

**다단계 서명**

- `/step` 은 LLM을 부르지 않는다 (크레딧 방어)
- 순서에 맞지 않는 `/step` 보고는 거절된다
- 중간에 끊긴 카드를 다시 열면 남은 단계부터 이어진다
- 마지막 `/complete` 에서만 대화가 이어진다
- 만료된 다단계 카드는 되살아나지 않는다

**프론트 (Vitest, 코로케이션)**

- 담당자 확인 전에는 서명·결제가 발생하지 않는다
- 서명 거절(4001)이 오류가 아니라 "거절됨"으로 반영된다
- 결제 리턴 후 대화가 이어진다

**스키마**

```bash
cd backend && bash scripts/verify-migrations.sh
```

## Acceptance Criteria

- BRAND 담당자가 `/agent`에서 만들고 싶은 제품을 말하면 에이전트가 부족한 정보를 되묻는다
- 소재·가공업체를 찾아 제시하고 견적을 비교해 설명한다
- **결제와 서명은 대화 말풍선 안의 카드로만 이뤄지고, 담당자가 누르기 전에는 아무것도 확정되지 않는다**
- AI 버튼을 누르면 별도 창이 뜨고, 다시 눌러도 창이 하나만 유지된다
- 두 창을 30분 이상 열어두어도 로그아웃되지 않는다
- 페이지를 새로고침해도 대화와 단계가 유지된다
- 담당자가 완료를 누르면 대화가 끝나고, 진행했던 건은 기존 화면에 그대로 남는다
- **동시 10명이 대화해도 다른 기능(소재 등록·결제·로그인)이 멈추지 않는다**
- 담당자가 화면에서 진행 중인 건도 대화가 조회해 설명한다
- 대기 구간(견적 도착, 배송, 가공 완료)에서 물으면 현황을 알려준다
- 모델이 단계에 없는 tool을 불러도 실행되지 않는다
- GMS 장애가 다른 도메인 기능을 멈추지 않는다
- 기존 소재·거래·가공·생산·제품 흐름의 회귀 테스트가 통과한다

## 1차 구현 범위 — 소재 조달 (INTAKE + MATERIAL_SOURCING)

공급업체→브랜드 거래 구간부터 만든다. 결제 1회 + 서명 2회로 **"대화창에서 결제와 서명만"** 을
완전히 보여줄 수 있으면서, 생산(서명 4회)보다 실패 지점이 훨씬 적다.

| tool | 종류 | 위임 |
|---|---|---|
| `save_requirement` | 읽기 | 대화에 요구사항 고정 |
| `set_phase` | 읽기 | 단계 이동 |
| `get_my_materials` | 읽기 | `MaterialQueryService` |
| `search_listings` | 읽기 | `ListingQueryService` (온체인 여부 표시) |
| `quote_trade` | 읽기 | `TradeCommandService#quote` |
| `get_shipping_default` | 읽기 | `CompanyProfile` + `User` |
| `purchase_material` | 💰 PAYMENT | `TradeCommandService#create` + `PaymentService#ready` |
| `request_chain_order` | ✍️ WALLET_SIGN | 프론트가 `createOrder` → chain-link |
| `confirm_receipt` | ✍️ WALLET_SIGN | `TradeReceiptService#confirmReceipt` |

`quote_trade` 를 따로 둔 이유는 **모델이 금액을 직접 곱해 말하지 못하게** 하기 위해서다.
반올림과 단위 환산이 서버에 있고, 보여준 금액과 청구액이 다르면 신뢰를 잃는다.

`get_shipping_default` 는 `TradeCreateRequest` 가 배송지 5개 필드를 필수로 받기 때문에 있다.
채팅에서 주소를 타이핑하게 하면 최악이고 오타가 나면 물건이 엉뚱한 곳으로 간다. 회사 등록
주소를 제안하고 담당자가 한 마디로 확인하게 한다.

가공·생산·제품 단계의 tool 은 아직 없다. 단계 모델과 카드 구조는 그대로 두었으므로 tool 만
추가하면 들어간다.
